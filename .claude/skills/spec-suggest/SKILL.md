# 仕様提案 (spec-suggest)

ミニゲームの仕様書には書かれていない実装の細部（演出、UX、AIの挙動など）について、
質問攻めにする代わりに、こちらから具体的な複数案とその推奨を即座に提示するスキル。

grilling/grill-meは「ユーザーに聞いて考えを固める」スキル。このスキルは逆に
「こちらから叩き台を複数出す」スキル。使い分けの目安は本ファイル末尾を参照。

## 進め方

### 1. 関連する仕様書を特定して読む

`Docs/*_SPEC.md` をGlobで探し、質問に関連しそうなファイルを読む。
どのミニゲームの話か文脈（開いているファイルのパス、直前の会話）から明らかならそれを使う。

仕様書全体を丸暗記する必要はない。質問に直結する箇所を重点的に踏まえる。

- **MVP方針・MVP対象外**: 提案が対象外機能（フォーメーション変更、オンライン対戦等）に
  踏み込んでいないか
- **対象プラットフォーム**: Android/iPhoneのタッチ操作やモバイル性能で無理なく動くか
- **アーキテクチャ境界**: `Common/`に置くべき処理と、ミニゲーム固有の処理を混同していないか
- **開発フェーズ/完了条件**: 今どのPhaseの話で、後回しでよい話ではないか

これらはCLAUDE.mdの「小さく作る」「Playable Build優先」「スコープ制御」という方針の判断材料になる。

### 2. 曖昧なら1ラウンドだけ確認する

質問がすでに具体的で、仕様書の情報と合わせて案を出すのに十分なら、確認なしで次のステップに進む。

以下のような、案の方向性が大きく変わってしまう前提が未確定な場合だけ、
grillingと同じ形式（❓ Qナンバー + 案2〜4個 + ⭐推奨）で**1ラウンドのみ**質問する。
2ラウンド目は行わない — 曖昧さが残っても、その時点の情報で提案に進む。

例: 「ゴール演出」と言われたが、画面演出・SE・選手アニメーション・スコア表示のどれを指すか
仕様書からも会話からも判断できない場合など。

### 3. 複数の実装案を提示する

以下の形式で、2〜4個の具体案を出す。コードは書かない — このスキルはアイデア出しに徹する
(実装コード自体は、案が決まったあとに通常のやり取りでCLAUDE.mdの方針に沿って提供する)。

```
💡 **<トピック>への提案**（参照: <該当する仕様書とセクション>）

- **案1: <案の名前>** — <何をするか。プレイヤーからどう見えるか>
  - メリット: <...>
  - コスト目安: <小/中/大。週末実装に収まるかの感覚値>
- **案2: <案の名前>** — <...>
  - メリット: <...>
  - コスト目安: <...>
- **案3: <案の名前>** — <...>（無理に3つにしなくてよい）

⭐ 推奨: 案N — <理由。「週末で実装し切れるか」を必ず判断基準に含める>
```

推奨の選び方はCLAUDE.mdの哲学と同じ: 一番作り込まれた案ではなく、
**この週末で実装し切るのに最も確実で簡単な案**を第一候補にする。
凝った案は「余裕があれば」の追加案として触れる程度にとどめる。

### 4. 決定はユーザーに委ねる

提案は叩き台であり、代わりに決めるものではない。ユーザーが案を選んだら、
そこから先の具体的な実装（ステップとC#コード）は通常のCLAUDE.md方針に従って進める。

## grilling/grill-meとの使い分け

- **grilling**: まだ何も決まっていない設計判断を、ユーザーに質問しながら一緒に固めていきたいとき。
  意思決定はユーザーがする。
- **spec-suggest**: 大枠の仕様はすでに決まっていて（Docs/の仕様書に書いてある）、
  書かれていない細部を埋めるための具体案がすぐ欲しいとき。こちらから叩き台を出す。

迷ったときは、ユーザーが「一緒に考えを整理したい」なら grilling、
「とりあえず案をいくつか出して」なら spec-suggest。
